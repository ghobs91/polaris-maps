## Context

Polaris Maps has a working drive-navigation pipeline: `routingService.computeRoute` returns `ValhallaRoute[]`, `navigationStore` holds `activeRoute`/`alternateRoutes`/`routePreviewAlternates`, `trackingService` projects GPS fixes onto the route polyline, and `app/(tabs)/navigation.tsx` renders `NextTurnBanner`, `LaneGuidance`, `SpeedLimitSign`, and `NavigationHud`. The gaps are behavioral, not architectural:

- `alternates` is hard-coded to `0` (`routingService.ts:450`) and though `alternateRoutes`/`routePreviewAlternates` are stored, no component reads them; only `routes[0]` is shown.
- Nothing advances or ends navigation: `stopNavigation` fires only from the Exit button, `currentLegIndex` changes only via the manual Skip action, and the destination maneuver just plays a haptic.
- TTS speaks once per step change (`navigation.tsx:100-126`); there is no distance ladder, no start/reroute/off-route prompt, no in-navigation mute/repeat, and `app.json` declares only `UIBackgroundModes: ["location"]`.
- Walk is a pedestrian-costed preview that then reuses the drive UI; bicycle exists in `CostingModel` with no UI; transit is itinerary preview only.
- `src/native/valhalla/index.ts:18-48` and `src/native/mapkit/index.ts:101-129` drop `lanes`/`speed_limit` (MapKit also drops `streetNames`/`verbalPostTransition`), so lane guidance and the speed-limit sign vanish on offline/fallback routes.
- `getGpsSpeed()` has no consumers; there is no along-route corridor search beyond waypoint results sorted by distance-to-polyline; no steps list during active navigation.

Constraints: iOS-only ship target; device TTS must remain free; `ios/` and `android/` are generated by `expo prebuild`, so native edits live in `plugins/native/PolarisMaps/` and are copied by `plugins/withValhalla.js`; `.specify/memory/constitution.md` requires integration tests per user-facing feature, unit tests per public function, and atomic commits.

## Goals / Non-Goals

**Goals:**

- Compute, display, select, and switch route alternatives with waypoints/preferences preserved.
- Detect waypoint and destination arrival; auto-advance legs and auto-end navigation behind settings, with an arrival summary and spoken/haptic announcement.
- Upgrade guidance voice into a distance ladder plus start/reroute/off-route prompts, with in-navigation mute/repeat and audibility while locked.
- Provide guided walk/cycle turn-by-turn and transit step-through on the existing guidance shell.
- Add current-speed + speed-limit-alert HUD, preserve lanes/speed limits on offline/fallback routes, along-route search, and an in-navigation steps list.

**Non-Goals:**

- Turn-by-turn lane-level guidance for walking (nonsensical) or transit (not road-based).
- Cloud/paid voice synthesis or downloaded neural voices.
- Android-specific behavior beyond not regressing shared code.
- New P2P protocols or traffic-mesh changes.

## Decisions

### D1. Alternatives: Valhalla-native request, degrade gracefully, preview + in-nav toggle

Request `alternates: 2` through the existing `alternates` option, threaded from `computeRoute` callers, and thread the same `avoidTolls/avoidHighways/avoidFerries` + waypoint list into every alternative so preferences and stops are preserved. Store into `routePreviewAlternates` (preview) and `alternateRoutes` (active). Render all alternative geometries on the map (selected route emphasized) and one card per alternative with duration, distance, and delay vs. the fastest.

- **Why not perturb the primary polyline to fake alternatives**: fabricated routes can be illegal/unbuildable and would break snap/voice. Rejected.
- **Why not always compute alternates**: extra latency/bandwidth and offline Valhalla/MapKit may not support them. Request alternates only when the provider path supports it (online Valhalla, native Valhalla) and fall back to a single route silently.
- **Switch during navigation**: reuse `replaceRoute`/`addWaypointAndReplaceRoute` semantics, re-threading current `waypoints`, `currentLegIndex`, and `costing`, then restart `startTracking` on the new geometry so dead-reckoning and arrival detection rebind. After switching, clear stale alternatives until the next recompute.
- **Tradeoff**: ETA thrash and large polylines; mitigate by capping alternates at 2 and only re-fetching on explicit recompute, not periodically.

### D2. Arrival: GPS radius AND route progress, debounced; auto-advance/auto-end are settings

Declare arrival only when both conditions hold: haversine distance from the current fix to the target (waypoint or destination) is within a radius (≈30 m waypoint, ≈40 m destination) **and** route progress (`trackingService` segment index vs. the leg/destination `endShapeIndex`, or remaining distance under a threshold) confirms the target is reached. Require N consecutive matching fixes / minimum approach speed decay to avoid drop-through false positives. A near-pass with substantial remaining distance does not count.

- **Why not radius-only**: a route passing close to the destination (parallel street, highway overpass) would falsely end navigation.
- **Why not progress-only**: GPS loss or DR drift near the end can stall progress; radius confirms the physical arrival.
- **Auto-advance legs** (`navigationAutoAdvanceLegs`, default on): on waypoint arrival, call the existing `advanceLeg` path. When off, show a "reached stop" prompt with Continue/Stop.
- **Auto-end** (`navigationAutoEnd`, default on): after arrival, show the summary; end navigation on summary dismiss or after a short delay, whichever first. When off, keep guidance active until the user exits.
- Arrival radius/thresholds are internal constants (not user-facing) and centralized so tests can inject them.

### D3. Voice: distance-band ladder + dedupe keys, interruption-safe TTS, background audio session

Replace step-change-only speech with a ladder evaluated on each GPS tick: bands (imperial ~1 mi / 0.5 mi / 0.2 mi; metric ~1 km / 500 m / 200 m, plus near bands) announced once per maneuver. Dedup key = maneuver identity (`beginShapeIndex` + `type`) + band; announce the largest un-announced band whose distance ≤ distance-to-maneuver, skipping bands already passed (e.g., navigation started mid-band). Reset keys on reroute and on new maneuver. Keep the existing step-change announcement as the short-range guarantee.

- **Start prompt**: speak "Starting navigation" once when `isNavigating` transitions true.
- **Reroute/off-route**: speak on `hasDeviated` rising edge ("Off route, rerouting") and when `isRerouting` falls (reroute complete), deduped.
- **Interruption handling**: keep one active utterance; `speakInstruction` already stops-then-speaks. Add an explicit in-flight guard and clear dedupe on `onDone`/`onError` so a cancelled prompt can be re-spoken (needed for Repeat). Repeat re-speaks the current maneuver's prompt unconditionally, bypassing the same-text dedupe.
- **In-navigation mute**: local override in `navigationStore` (not the global Settings toggle) that gates the TTS service and drives the HUD icon; unmute restores without touching `settingsStore.voiceGuidanceEnabled`. `ttsService` MUST consult both.
- **Background audio**: add `audio` to `UIBackgroundModes` and configure the speech `AVAudioSession` (`.playback`, `.duckOthers`, `.mixWithOthers`) so prompts survive lock. This must coexist with the existing background **location** session (`expo-location`, Live Activity); both share one `AVAudioSession`/app lifecycle, so activation must be idempotent and deactivated when navigation ends. If expo-speech cannot set the category, add a small config-plugin/native shim rather than a new dependency.
- **Why stay on expo-speech**: free, offline, device voices; a later change can swap engines behind the `ttsService` boundary.

### D4. All-mode: one guidance shell parameterized by mode; transit step-through is a sibling mode

Drive and bicycle reuse the exact same screen/pipeline (`routingService` with `costing: 'bicycle'`, `trackingService`, banner, ladder, arrival). Walking reuses them with `costing: 'pedestrian'` and a mode capability map. A `NavigationMode` derived from `costing` gates automotive-only widgets: `LaneGuidance`, `SpeedLimitSign`, and the speed HUD are hidden for `pedestrian`/`bicycle`; the steps list and arrival flow stay. The `TransportModeSelector` gains a bicycle pill and Walk becomes startable (not preview-only).

- **Why reuse over duplicate screens**: guidance, arrival, and voice logic are mode-agnostic; forking would triple the surface and violate cohesion. Only widget visibility and costing differ.
- **Transit**: OTP itineraries are already in `transitStore` (`itineraries`, `selectedItineraryIndex`). Implement step-through as a mode of the same screen that advances through itinerary legs/steps on user action (or GPS where a walk leg applies) and renders transit-appropriate cards; it does **not** use road maneuver snapping. Reuse the HUD shell/arrival summary, not the lane/speed widgets.
- **Data limits**: bicycle is offered only when the costing/data exists; walking transit first/last-mile legs may use the pedestrian costing where geometry is available.

### D5. Native mappings: extend the source-of-truth Swift in `plugins/native/` and TS adapters

`ios/` is wiped by `pnpm prebuild`; the canonical native sources are `plugins/native/PolarisMaps/*.swift`, copied into `ios/PolarisMaps/` by `plugins/withValhalla.js`. Add `speed_limit` and `lanes` to the Valhalla maneuver dictionary and `street_names`/`verbal_post_transition` (and any available speed/lane data) to the MapKit maneuver dictionary, mirror to the checked-in `ios/PolarisMaps/` for immediate local builds, extend `NativeValhallaRoute`/`NativeMapKitRoute` TS types, and map them in `src/native/valhalla/index.ts` and `src/native/mapkit/index.ts` (reusing the existing `parseLaneGuidance`, already used by the online path).

- **Why the JS adapters were the visible loss**: the online path maps lanes/speed_limit already; offline/fallback drop them, so lane guidance and the sign disappear. Restoring the mapping (native + TS) is the minimal fix and keeps one `ValhallaRoute` shape.
- **MapKit reality**: `MKDirections` may not expose lanes or speed limits; where the native payload has no such data there is nothing to preserve, and the UI simply omits the widgets (same as today). `streetNames`/`verbalPostTransition` restoration still improves MapKit voice/instructions. Verify the pinned valhalla-mobile `Maneuver` model exposes these fields.

### D6. Safety HUD: derive from existing signals, no new sensing

Current speed comes from `getGpsSpeed()` (m/s → user unit via `useMetric`). Speed-limit changes are detected when `currentManeuver.speedLimitMph` changes (and between maneuvers where possible); over-speed fires when current speed exceeds the limit by a threshold and is debounced/hysteretic to avoid churn. Along-route search runs POI/result queries against a corridor around the active route polyline (reusing distance-to-polyline utilities) rather than a radial search. The steps list is derived from `activeRoute.legs.flatMap(l => l.maneuvers)` and highlights `currentStepIndex`.

## Risks / Trade-offs

- **Alternates unsupported offline / on MapKit** → request only on supporting paths; single-route fallback; card list simply hides.
- **False or missed arrival** → require radius AND progress with debouncing; centralize thresholds; unit-test near-pass and GPS-loss cases.
- **Auto-end surprises (user still needs the map)** → default-on but instantly configurable; show summary first; never auto-end before the final maneuver is reached.
- **TTS interruption/overlap and reroute spam** → one in-flight utterance, dedupe keys, rising-edge triggers, mute gate; integration-test off-route → reroute phrasing.
- **Background audio + background location contention or battery** → activate audio only during active guidance, idempotent session activation, deactivate on end; verify lock-screen behavior on device.
- **App Store review of `audio` background mode** → document that audio is used solely for navigation prompts; no continuous playback otherwise.
- **Mode leakage (lane UI on walking)** → single capability map keyed by costing; snapshot tests per mode.
- **Native edits lost by prebuild** → edit `plugins/native/` first, mirror to `ios/`, verify plugin copy; note this in tasks.
- **Larger polylines/CPU for alternates** → cap at 2, no periodic refetch.

## Migration Plan

1. Ship behind defaults; no data migration (all state is in-memory Zustand).
2. Native: update `plugins/native/PolarisMaps/` Swift, add `audio` background mode, run `pnpm prebuild` only with explicit approval (wipes `ios/`/`android/`) or hand-mirror into `ios/` for immediate local builds; `pnpm ios:pods` if the SPM/Pods change.
3. Rollback: revert the change's commits; the native background-audio bit and Swift mapping are additive and inert if unused; no persisted schema to unwind. If voice ladder causes issues, fall back to step-change speech (current behavior) via the mute/feature path.
