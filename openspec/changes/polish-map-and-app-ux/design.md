## Context

Polaris Maps is a React Native 0.86 / Expo SDK 57 (bare workflow) app that ships iOS only. The relevant current state, verified in the repository:

- POIs are fetched only at zoom >= 14 (`POI_MIN_ZOOM` in `src/components/map/MapView.tsx`), then thinned by a greedy pixel-exclusion filter in `src/utils/poiSpatialFilter.ts` (caps 100 at z<14 rising to 420 at z>=17) and rendered as React Native `MarkerView`s in `src/components/map/POILayer.tsx`. Below z14 they are cleared, not clustered.
- A complete theme system exists (`src/contexts/ThemeContext.tsx` with `light | dark | system` from `settingsStore`, `app.json` `userInterfaceStyle: automatic`), but many files import the static light `colors`; `src/components/regions/RegionGate.tsx` uses `useColorScheme()` directly; `app/(tabs)/index.tsx` hard-codes `#F2F2F7`.
- Map chrome is absent: no compass, scale bar, zoom/rotate/pitch controls; `MapView` uses a default `<UserLocation>` with no heading indicator; pitch is fixed at 60 only in navigation mode.
- `terrain` exists in the `mapStore` `mapStyle` union but is ignored by `src/components/map/mapStyleResolver.ts`; there is no DEM/hillshade, and the Layers card offers only Default/Satellite.
- `react-native-reanimated` 4.5.0 and `react-native-worklets` 0.10.0 are declared but never imported in app code, `babel.config.js` has an empty plugin list, and `react-native-gesture-handler` is not a direct dependency. All sheets use legacy `Animated`/`PanResponder` with differing snap thresholds.
- Live Activities exist (`src/hooks/useLiveActivity.ts`, `plugins/native/PolarisMapsLiveActivity/`, `plugins/withLiveActivities.js`); CarPlay is mature. There are no widgets, App Intents, or share extension.
- `ios/` is regenerated by `expo prebuild --clean`, so every native addition must be delivered by a config plugin under `plugins/`, following the existing `withLiveActivities.js` pattern.

The project constitution makes UX consistency (Principle III: map interactions respond within 100ms, offline/degraded states visually distinct) and performance (Principle IV: 60fps tile rendering during pan/zoom, frame drops below 30fps are P1) non-negotiable; both constrain the decisions below.

## Goals / Non-Goals

**Goals:**

- Show meaningful POI density at every zoom: clusters below the individual-marker threshold, individual markers and labels at high zoom.
- Make System/Light/Dark a real, app-wide setting across every user-facing surface, including gated and modal ones.
- Make map controls and selectors usable with VoiceOver, size text with Dynamic Type without clipping, and meet contrast targets in both themes.
- Provide standard map chrome (compass, scale, heading puck, rotate/pitch) and a working terrain mode using free/open data.
- Deliver a home-screen widget and Siri/App Intents reusing existing state, sharing one source of truth with Live Activities, with no server or paid service.
- Replace four bespoke sheet animations with one Reanimated + Gesture Handler primitive and add undo for destructive actions.

**Non-Goals:**

- Android parity for the polish work (iOS is the ship target; keep code cross-platform where free, but do not build Android widgets/intents).
- Replacing the POI data pipeline or online/offline fetch logic beyond adding a bounded low-zoom tier.
- New map tile providers or paid imagery; terrain DEM sourcing must be free/open and coordinated with `broaden-traffic-and-media-sources`.
- A full design-system rewrite; this change moves existing components onto the theme and one sheet primitive, it does not restyle the app.

## Decisions

### D1. Cluster in JS and render cluster badges as MarkerView (not native GeoJSON clustering)

Two options were considered:

- Native MapLibre GeoJSON clustering (`ShapeSource cluster`) with symbol layers and `getClusterExpansionZoom`: GPU-side, best raw performance, built-in count/expansion. But it would duplicate the existing POI tap/selection pipeline, split theming between map-style layers and RN components, and make rich, themed, category-colored badges and label handling awkward alongside the current `MarkerView` path.
- JS clustering into a bounded set of cluster descriptors, rendered as `MarkerView` badges alongside the existing individual-marker path.

Chosen: JS clustering. Low-zoom cluster counts are bounded (target <= 200 cluster badges), the algorithm is O(n) over the already fetched/cached set, and it preserves a single theming and tap/selection path. A hybrid (native clustering only when JS would exceed the cap) is explicitly deferred.

Concretely: add `clusterPoisForDisplay(pois, bounds, zoom)` that maps each POI to screen pixels via the existing `toPixel` math and buckets into grid cells sized to a marker footprint; each cell emits `{ lat, lng, count, poiIds, dominantCategory }` at its centroid. Single-POI cells render the existing `PoiBadge`; multi-POI cells render a new `ClusterBadge` (count + dominant category color) that is themed and accessible. Cluster tap calls `cameraRef.setCamera` to the cluster's expansion zoom.

**60fps budget (Constitution IV):** clustering is recomputed only on `onRegionDidChange` (gesture settled), never on `onRegionIsChanging`, so no per-frame JS work runs during pan/zoom. Results are memoized on `(pois, bounds, zoom)` and the rendered marker count is capped. Camera-driven expansion uses a single animated `setCamera`, not per-frame state updates.

**Data for low zoom:** the current single fetch tier is insufficient. Add a bounded low-zoom tier: phase 1 reads cached Overture places from SQLite (`getPlacesInBounds`) so offline works with zero network; phase 2 optionally fetches a capped Overture/PMTiles page online. Expensive Overpass queries are skipped below the cluster threshold. This keeps low-zoom fetching cheap and the offline path identical to the existing cached-first flow.

### D2. Theme migration via a `useThemedStyles` hook, migrated in priority batches

Migrate files from static `colors` imports to `useTheme()`. To avoid re-creating style objects on every render and to avoid touching unrelated code, introduce a small helper (`useThemedStyles(createStyles)` / memoized `createStyles(isDark)`), which already has precedent in `SettingsContent.tsx`. Structural styles stay static; only color-dependent values move into the themed factory. Migration proceeds in batches (map tab hard-coded background first, then detail/region screens, then search/regions components, then remaining imports). Gated surfaces (`RegionGate`, `GeofabrikTreePicker`) switch to `useTheme()` so a manual Light/Dark choice overrides the OS scheme. A lint guard (allowlist or custom rule) prevents new static light-color imports, so the migration cannot regress.

Alternatives considered: per-file `useColorScheme()` (rejected: ignores the in-app preference and caused the current `RegionGate` bug); a global mutable color object (rejected: breaks React re-render and dark/light switching).

### D3. Dynamic Type via constraints, not blanket scaling

`allowFontScaling` is on by default, so the real problem is fixed 44-48px heights clipping large text. Decision: replace fixed `height` with `minHeight` and scrollable containers on content screens; define a small set of `maxFontSizeMultiplier` caps for dense, map-anchored overlays (POI labels, cluster counts, map chrome) so accessibility text sizes do not turn the map into an unreadable pile. Body text on settings/detail screens scales fully. Reduce Motion (via `AccessibilityInfo`) suppresses camera fly and sheet spring animations.

### D4. Reanimated 4 + Gesture Handler adoption, incremental behind one shared sheet

Reanimated 4.x requires the worklets Babel plugin (`react-native-worklets/plugin`), not the reanimated plugin path used in v3; the exact plugin is verified against the installed versions before implementing. `react-native-gesture-handler` must be added as a direct dependency (it is not currently declared in `package.json`). A single bottom-sheet primitive (snap points, drag handle, velocity/threshold rules as design tokens) is built first, then `FloatingSearchPanel`, `POIInfoCard`, `NavigationHud`, and `NodeDashboardDrawer` migrate to it one at a time, each verified independently. Legacy `Animated` code stays until its component is migrated, so there is no big-bang risk. Haptics (`expo-haptics`) fire on snap, locate, and destructive confirmation.

### D5. iOS widget/App Intents as config-plugin-owned native targets with one shared state writer

`expo prebuild --clean` wipes `ios/`, so hand-editing is forbidden. A new config plugin (mirroring `withLiveActivities.js`) will copy Swift sources, add the WidgetKit extension and App Intents targets to the Xcode project, and add App Group entitlements. The app writes a small, versioned state snapshot (active destination, ETA, remaining distance, saved/Home place) into a shared App Group container from one module; the widget, App Intents, and Live Activities all read that same location, so values cannot diverge. `NavigateHomeIntent` reads the Home favorite and deep-links `polaris-maps://` to start navigation; if no Home is set it opens the app to set one. Everything is on-device; no server or paid dependency.

## Risks / Trade-offs

- [Low-zoom POI data may be sparse or stale, making clusters misleading] -> Cluster counts come only from cached/available POIs; label the count as places known, use cached-first fetch, and never fabricate density. Validate against region-pack coverage.
- [JS clustering could regress map frame rate if run during gestures] -> Recompute only on settled region events, memoize, cap markers, and add a before/after benchmark as a merge gate (Constitution IV).
- [Theme migration touching ~33 files risks conflicts and unrelated churn] -> Batch by directory, use the memoized style factory, keep structural styles untouched, and add a lint guard; each batch is its own atomic commit.
- [Reanimated 4 migration can break existing gesture behavior or the Babel plugin misconfiguration can fail the build] -> Verify the worklets plugin against installed versions, migrate one sheet at a time, keep legacy implementations until each is proven, and rely on lint/typecheck/tests per commit.
- [Widget/App Intents native wiring is fragile across `prebuild --clean` and Xcode upgrades] -> Own it entirely through config plugins, mirror the proven Live Activities plugin, and verify a clean `expo prebuild` regenerates working targets before shipping.
- [Dynamic Type caps could fail accessibility expectations] -> Cap only dense map overlays; keep all content text fully scalable and document the rationale.
- [Terrain DEM adds a new external data dependency] -> Use a free/open DEM with clear attribution, degrade to the base style when offline/weak-link (consistent with Principle III), and coordinate sourcing with `broaden-traffic-and-media-sources`.
- [Widget refresh budget limits ETA freshness] -> Rely on timeline updates and Live Activities for live ETA; the widget shows last-known state with a timestamp.

## Migration Plan

1. Foundations first: add the Babel plugin and Gesture Handler, build the shared sheet and toast primitives, and migrate sheets one at a time (no behavior change expected).
2. Theme migration in batches, each an atomic commit, with the lint guard added once the first batch lands.
3. Low-zoom POI tier and JS clustering, benchmarked before merge.
4. Map chrome and terrain, independent of the other streams.
5. iOS widget/App Intents last, since it depends on stable navigation/place state and native plugin verification.
6. Rollback: each stream is independently revertible. Clustering can fall back to the current hide-below-z14 path behind a constant; sheet migration can retain legacy components until fully replaced; theme batches revert cleanly per commit; terrain falls back to the existing default style; native targets can be disabled by removing the config plugin and re-running prebuild.

## Open Questions

- Exact cluster zoom threshold and grid cell size (start with individual markers at z>=14, clustering z<14; tune on device).
- Whether to move all POI rendering to native symbol layers long-term if POI volume grows beyond the JS cluster cap.
- Which free DEM provider to standardize on (including terrarium vs. custom encoding) and how it interacts with offline region packs; to be resolved with `broaden-traffic-and-media-sources`.
- Whether the widget should show only saved places or also the last searched destination, and the desired refresh cadence within the OS budget.
- Whether Dynamic Type caps should be user-visible/configurable or fixed.
