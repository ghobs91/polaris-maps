## Context

Turn-by-turn guidance is implemented inside `app/(tabs)/navigation.tsx` as a screen-scoped effect:

- `Location.watchPositionAsync({ accuracy: BestForNavigation, distanceInterval: 5, timeInterval: 1000 })` feeds a GPS callback that snaps to the route polyline (`snapToRoute`), updates a dead-reckoning (DR) anchor, detects off-route deviations (triggering `reroute()` from `routingService`), advances maneuver steps against `beginShapeIndex`, and pushes ETA/remaining distance into `useNavigationStore`.
- A `requestAnimationFrame` loop interpolates position/bearing between GPS ticks into **component-local state** (`setNavPosition`/`setNavBearing`) for smooth camera gliding.
- A Live Activity (`useLiveActivity`) already mirrors nav state to the lock screen, and CarPlay mirrors it via `carPlayManager.ts` subscribing to `navigationStore`.

When the user backgrounds the app or locks the phone, iOS suspends the process: no JS runs, the watcher stops, guidance freezes. There is no `UIBackgroundModes` entry, no background-location permission request, and no `expo-task-manager` dependency today.

Constraints:

- Bare workflow; `ios/` is generated by `expo prebuild` — all config must go through `app.json` / config plugins.
- Expo SDK 57; `expo-location@57.0.6` is installed; `expo-task-manager` is not.
- Scope locked to iOS for this change (Android already has `ACCESS_BACKGROUND_LOCATION` declared but its foreground-service wiring is deferred).
- Repo constitution requires unit tests for public functions and integration tests for user-facing features.

## Goals / Non-Goals

**Goals:**

- Active navigation continues uninterrupted (position updates, step advancement, ETA, rerouting, Live Activity, voice prompts) while the app is backgrounded or the screen is locked on iOS.
- Identical tracking behavior foregrounded vs backgrounded — one shared pipeline, not duplicated logic.
- Graceful degradation: if the user denies background location, navigation still works exactly as it does today (foreground-only).
- Session lifecycle fully tied to navigation state: starts on `startNavigation`, stops on `stopNavigation`; no location activity outside active navigation.

**Non-Goals:**

- Android foreground-service support (deferred; Android behavior unchanged by this change).
- Continuous background location outside active navigation (e.g., traffic probe collection in background — separate concern).
- Lock-screen UI changes beyond what the existing Live Activity already renders.
- Changes to routing, Valhalla integration, CarPlay contracts, or store shapes consumed by other features (beyond adding new state).

## Decisions

### D1: Single managed location session instead of watcher + parallel background task

Replace the screen's `watchPositionAsync` with one `expo-location` background-capable session: `TaskManager.defineTask(BACKGROUND_LOCATION_TASK, handler)` registered at module load, and `Location.startLocationUpdatesAsync(BACKGROUND_LOCATION_TASK, { accuracy: BestForNavigation, pausesUpdatesAutomatically: false, showsBackgroundLocationIndicator: true, timeInterval/distanceInterval equivalent to current })`.

Rationale:

- `startLocationUpdatesAsync` deliveries work in the foreground too, so one code path serves both modes; there is no risk of two watchers fighting over the DR anchor or double-firing reroutes.
- Alternative considered: keep `watchPositionAsync` for foreground and add a second background task — rejected because both streams would need deduplication and the DR/off-route state machine would see interleaved sources.
- Fallback path: if background permission ("Always") is denied, fall back to the existing `watchPositionAsync` foreground-only watcher so behavior never regresses.

Note: when the app process is alive (foreground), the TaskManager handler executes in the same JS context — no headless relaunch complexity during normal navigation.

### D2: Extract GPS processing into `src/services/navigation/trackingService.ts`

Move the entire pipeline out of the React effect into a plain singleton service:

- `startTracking(route)` — decodes polyline, builds maneuver list, resets state
- `processFix(location)` — snap-to-route, off-route detection + `reroute()` trigger, DR-anchor update with no-backwards-jump rule, step advancement, ETA update (all exactly the logic currently inline in the effect)
- `stopTracking()` — clears state

The service holds mutable internal refs (DR anchor, GPS segment index, off-route counter, rerouting flag) — same data currently in `useRef`s. Rerouting, store updates (`advanceStep`, `updateEta`, `replaceRoute`), TTS, and haptics are invoked through the same modules used today. This makes the pipeline unit-testable without React, satisfying the constitution's testing requirements.

### D3: New live-position store `src/stores/navigationTrackingStore.ts`

`navPosition`, `navBearing`, and `distanceToTurn` move from component `useState` into a small Zustand store that `trackingService.processFix` writes and the screen reads. The 60fps dead-reckoning _interpolation_ loop stays in the screen component (it's a rendering concern and irrelevant when backgrounded); it reads anchors from the tracking service rather than local refs.

Rationale: headless code cannot write React state; Zustand matches every other cross-boundary signal in this app (`navigationStore`, `trafficStore`, …).

### D4: Permission strategy — request "Always" lazily at navigation start

On `startNavigation`: check `getBackgroundPermissionsAsync()`. If undetermined, show an in-app explainer, then `requestBackgroundPermissionsAsync()`. If granted → managed background session; if denied → foreground-only fallback (D1). Never request at app launch.

Rationale: Apple rejects Always-permission apps that can't justify it at request time; mid-flow "you're about to navigate" is the strongest justification moment, matching Google Maps' approach.

### D5: Config via `app.json` + plugin options

- `ios.infoPlist.UIBackgroundModes: ["location", "audio"]` — `audio` is included so expo-speech (TTS prompts) keeps playing while locked, per the "voice prompts continue" requirement; the app has genuine audible content (turn instructions), satisfying App Review's expectation for the audio mode
- Update location usage strings (`NSLocationWhenInUse…` / `NSLocationAlwaysAndWhenInUse…`) to explicitly cover turn-by-turn guidance in the background (current copy mentions traffic contribution only)
- No Android-side changes

Requires `pnpm prebuild` + pod install + native rebuild before this is testable on device; documented in tasks.

### D6: New dependency `expo-task-manager`

Required API surface for `startLocationUpdatesAsync`. Pin to the SDK 57-matched version (install via `npx expo install expo-task-manager`). This is the only new dependency; a custom native location module was considered and rejected as unnecessary work given `expo-location` already exposes everything needed.

## Risks / Trade-offs

- [Apple review scrutiny of background location] → Usage strings explicitly name turn-by-turn guidance; permission requested in navigation flow, not at launch; session stopped deterministically on `stopNavigation` and on route completion.
- [Battery drain during long navigations] → `BestForNavigation` is already used today; `pausesUpdatesAutomatically: false` is required for guidance correctness; session lifetime strictly bounded by navigation.
- [iOS may still suspend if "Always" not yet granted but user picked "While Using"] → Blue-pill background indicator (`showsBackgroundLocationIndicator`) keeps the session alive with WhenInUse authorization; verified behavior, plus foreground-fallback remains available.
- [Refactor regression risk in core guidance loop] → Extraction is mechanical (move logic verbatim into service); unit tests ported around the extracted functions cover happy path, off-route boundary, premature-step-advance guard, and DR no-backwards rule before touching the screen.
- [JS relaunch edge case: OS kills app then relaunches task headless] → Task handler checks `isNavigating` and exits early if navigation is not active, preventing zombie location sessions after crashes/reboots.

## Migration Plan

1. Add `expo-task-manager`, extract tracking service + store behind unit tests (no behavior change; screen still uses old path until switched).
2. Flip `navigation.tsx` onto the shared pipeline with fallback watcher.
3. Wire lifecycle into `startNavigation`/`stopNavigation` + add `app.json` changes.
4. `pnpm prebuild && pnpm ios:pods`, build to device, verify: lock-screen continuation, background reroute, Live Activity updates, session stops on arrival/cancel.
5. Rollback = revert commit; config reverts cleanly with next prebuild.

## Open Questions

- None blocking. Route-completion detection (auto-stop at destination) exists partially via step exhaustion; if gaps are found during implementation, auto-stop-on-arrival stays out of scope and is tracked separately.
