## Context

Offline region downloads are owned by a module-level singleton (`src/services/regions/downloadManager.ts`), not a screen. `startBackgroundDownload()` aborts/attaches per region, mirrors `DownloadProgress` into `useRegionDownloadStore` via `emit()`, and resumes interrupted downloads on `AppState === 'active'`. The store exposes `progressByRegion` and `activeIds`.

A working ActivityKit stack already exists for navigation:

- `plugins/native/PolarisMaps/NavigationAttributes.swift` — `ActivityAttributes`
- `plugins/native/PolarisMaps/PolarisLiveActivity.swift` + `.m` — `RCT_EXTERN_MODULE` bridge with `isSupported`/`start`/`update`/`end`
- `plugins/native/PolarisMapsLiveActivity/NavigationLiveActivity.swift` — Lock Screen + Dynamic Island widget
- `plugins/native/PolarisMapsLiveActivity/PolarisMapsLiveActivityBundle.swift` — `WidgetBundle`
- `plugins/withLiveActivities.js` — config plugin that copies Swift sources into `ios/` and registers them in the app target and extension target

`NSSupportsLiveActivitiesFrequentUpdates` is already enabled, so frequent progress updates are permitted.

Constraints:

- `ios/` is generated by `expo prebuild`; all native wiring must go through config plugins (`withLiveActivities.js`) and committed source under `plugins/native/`.
- Live Activities **cannot be started from the background on iOS** — `Activity.request` must be issued while the app is still foreground. The only reliable moment is the `inactive` transition (the app is resigning active but not yet suspended), with `background` as a best-effort retry.
- JS is suspended shortly after the app backgrounds (a short grace window remains). Progress updates therefore stop when the OS suspends the process; the activity shows the last-known progress and is dismissed when the app returns to the foreground.
- Repo constitution requires unit tests for public functions; widget rendering itself is verified manually on device.

## Goals / Non-Goals

**Goals:**

- While the app is backgrounded and at least one region download is active, show a single Live Activity / Dynamic Island presentation with aggregate progress.
- Aggregate representation: combined percent across active regions, active region count, current stage label, and the region name when exactly one is active.
- Lifecycle owned by app-global code (not a screen), driven by `AppState` + `useRegionDownloadStore`.
- No behavior change to downloads, the Regions UI, or the navigation Live Activity.
- Graceful no-op when Live Activities are unavailable or unauthorized.

**Non-Goals:**

- True OS-level background `URLSession` downloads (the existing manager is JS-driven; unchanged).
- Android equivalent (foreground-service notification) — out of scope.
- A Live Activity while the app is foregrounded (explicitly excluded by product decision).
- Interactive controls (pause/cancel) from the Live Activity — read-only progress for this change.
- Multiple simultaneous Live Activities (one per region); a single aggregate activity is used.

## Decisions

### D1: Reuse the existing `PolarisLiveActivity` module with a second activity type

Add `currentDownloadActivity: Activity<DownloadAttributes>?` and `startDownloadActivity` / `updateDownloadActivity` / `endDownloadActivity` to `PolarisLiveActivity.swift`, and reflect them in `PolarisLiveActivity.m`. Share `DownloadAttributes.swift` between the app target and the widget extension (same as `NavigationAttributes.swift`).

Rationale: one bridge module, one config-plugin registration path, symmetric with navigation, no duplication. A separate `PolarisDownloadLiveActivity` module was considered and rejected — it would require a second bridging entry and more plugin code for no benefit.

### D2: New `DownloadAttributes` content model

```swift
struct DownloadAttributes: ActivityAttributes {
    struct ContentState: Codable, Hashable {
        var percent: Int              // 0...100 aggregate
        var regionCount: Int          // active downloads
        var label: String             // region name, or "2 regions"
        var stage: String             // human label, e.g. "Downloading map tiles"
        var isComplete: Bool          // final state styling
    }
}
```

Static attributes carry no per-download data (the activity is generic), so the struct has only `ContentState`. `label` and `stage` live in `ContentState` because they change as regions start/finish and stages advance.

### D3: Aggregate computation is a pure function

`computeDownloadAggregate(progressByRegion, activeIds)` in `downloadLiveActivity.ts` returns `{ percent, regionCount, label, stage, isComplete } | null`:

- Filter to ids that are in `activeIds` **and** not in a terminal stage (`complete`/`error`).
- `regionCount` = filtered length; return `null` when 0.
- `percent` = rounded mean of each active region's `percent` (equal weight per region), clamped 0–100.
- `label` = the single region's `regionName` when `regionCount === 1`, else `"${regionCount} regions"`.
- `stage` = the human-readable stage of the most recently updated active region.

Pure and unit-testable without React or native modules.

### D4: Background-only lifecycle owned by a module initializer

`src/services/regions/downloadLiveActivity.ts` exports `initDownloadLiveActivity()` (idempotent), called once from `app/_layout.tsx` (mirroring `initNavigationBackgroundSession()`). It:

- Subscribes to `AppState`; on `inactive` **or** `background`, if an aggregate exists and the native module is present, starts the activity (guarded so the first successful transition wins). Authorization is enforced natively via `ActivityAuthorizationInfo().areActivitiesEnabled`, so the JS side does not need an async support check.
- Subscribes to `useRegionDownloadStore`; while the activity is active, pushes throttled updates (≤1/second, and only when `percent`/`label`/`stage` meaningfully change).
- On `active`, ends the activity immediately.
- If the aggregate becomes `null` while the activity is active (all downloads finished/cancelled in the background grace window), updates the final `isComplete` state and ends with a short dismissal delay.

Rationale: downloads are app-global; a screen-scoped hook (the navigation pattern) would stop if the owning screen unmounts. A module initializer runs for the whole process lifetime and is directly testable by injecting a fake store snapshot.

### D5: Start attempt on `inactive`, retry on `background`

`AppState` on iOS fires `active → inactive → background`. Starting on `inactive` is the last moment `Activity.request` is reliably permitted; `background` is attempted as a second chance if the first failed. A start-failure flag prevents log spam. This is the pragmatic compromise for the "cannot start from background" platform constraint and is documented as a risk.

### D6: Optional `regionName` on `DownloadProgress`

Add `regionName?: string` to `DownloadProgress` (`downloadService.ts`). `downloadManager.startBackgroundDownload` wraps `emit` per region to attach `region.name`. Existing consumers ignore the extra field.

### D7: Native end policy

`endDownloadActivity(immediate: boolean)`:

- `immediate: true` when the app returns to foreground (remove promptly).
- `immediate: false` on background completion — `dismissalPolicy: .after(Date().addingTimeInterval(4))` so the user sees 100%.

### D8: No new dependencies

Only existing React Native/Expo APIs (`AppState`) and the current ActivityKit setup are used.

## Risks / Trade-offs

- **[ActivityKit may reject a start issued from `inactive`/`background` on some iOS versions]** → Attempt on `inactive` first (most likely to succeed), retry on `background`; failures are caught and logged, never crash. Worst case the activity does not appear but downloads are unaffected. If device testing shows this is unreliable, the fallback is to start while foreground and dismiss on `active` (product decision would need revisiting).
- **[Progress freezes when iOS suspends JS]** → Expected: the activity reflects last-known progress and updates again if JS runs during the grace window; it is always dismissed on foregrounding. This is inherent to JS-driven downloads and not regressed by this change.
- **[Transient `inactive` (Control Center, notification shade, incoming call) briefly shows the activity]** → The activity is ended as soon as the app becomes `active` again; acceptable flicker, and arguably informative while a download is active.
- **[Widget extension build breakage after adding a second widget]** → The config plugin already registers attributes in both targets; new files follow the exact same pattern and are verified with `pnpm prebuild` + a device build.
- **[Pre-existing test-suite failures]** → New unit tests are run in isolation and reported honestly; pre-existing failures are not attributed to this change.

## Migration Plan

1. Add `DownloadAttributes.swift`, `DownloadLiveActivity.swift`, and bundle/native-module changes behind the config plugin; extend `withLiveActivities.js`.
2. Add the TS native wrapper + pure aggregate helper + lifecycle service with unit tests (no UI/behavior change until initialized).
3. Initialize from `app/_layout.tsx` and add `regionName` to `DownloadProgress`.
4. `pnpm prebuild && pnpm ios:pods`, build to device; verify: start a download → background the app → Dynamic Island/Lock Screen shows aggregate progress → return to foreground dismisses it; completion while backgrounded shows 100% then dismisses; cancel/error removes it.
5. Rollback = revert the commit; config reverts cleanly on next prebuild.
